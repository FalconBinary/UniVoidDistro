Requirements not met (4):
  uefi: On ARM64 the verified boot chain of this system needs UEFI (servers, laptops: Limine, the signed UKI, Secure Boot with our keys); a Raspberry Pi boots from its own firmware.
    residual risk: The board's firmware boots the kernel unverified: whoever holds the board for a while can replace it and read what is typed.
    fix: A UEFI firmware for the board where one exists [VERIFY], or the Raspberry Pi's own secure boot, which the installer never sets up: its key goes into the board's OTP memory irreversibly (docs/uni/rpi.md).
  secure-boot: Secure Boot with the system's own keys verifies the bootloader and the UKI before they run.
    residual risk: The boot chain is not verified: an evil maid can replace the kernel and capture the LUKS passphrase.
    fix: Enable Secure Boot support (Custom or Standard mode) in the firmware setup; the system enrols its own keys after the first boot (install/20-firstboot.sh).
  tpm2: A TPM 2.0 measures the boot (tpm2-totp shows that it is unchanged) and its event log lists the Option ROMs whose hashes the key enrolment must keep.
    residual risk: No TPM 2.0: no tpm2-totp against an evil maid, no measured boot, and no Option ROM check before the Secure Boot keys are enrolled (the Microsoft certificates are then kept).
    fix: Enable the firmware TPM (Intel PTT, AMD fTPM) or the TPM module in the firmware setup.
  iommu: An IOMMU confines every device's DMA to the memory the kernel gives it.
    residual risk: No IOMMU: a malicious or compromised device (Thunderbolt, ExpressCard, a PCIe card) can read and write all memory by DMA.
    fix: Enable VT-d (Intel) or AMD-Vi / IOMMU (AMD) in the firmware setup; a virtual machine needs an emulated IOMMU (QEMU: -device intel-iommu).

notes (1):
  A Raspberry Pi has no UEFI, so VH_SECURITY=strict refuses it (the uefi requirement): nothing verifies the kernel it boots. VH_SECURITY=tiered installs it with that risk confirmed.
