# Spike S1: sched_ext with the BPF program and the loader both in Zig

**Verdict: go.** A sched_ext scheduler whose BPF programs and loader are written in Zig
0.17.0 only (no libbpf, no clang, no C) loads and runs on Linux 6.18.57 with
`CONFIG_SCHED_CLASS_EXT` under `lockdown=confidentiality`, on arm64 (QEMU hvf) and on
x86_64 (QEMU TCG). Neither fallback of the roadmap (A: the policy in Zig user space, B: a
BPF bytecode emitter in Zig) is needed. The code is `sched/` and the new
`zig/lib/{bpf_uapi,btf,elf}.zig`; the rig is `sched/test/`; the raw serial logs of the
final runs are [S1-arm64-serial.log](S1-arm64-serial.log) and
[S1-x86_64-serial.log](S1-x86_64-serial.log) (2026-10-19).

## The checks the task asked for

**Lockdown.** `/sys/kernel/security/lockdown` shows `none integrity [confidentiality]`
(set on the command line; `CONFIG_LSM="lockdown"`). The scheduler needs nothing the
lockdown withholds: the `exit` callback reads `scx_exit_info.kind/exit_code/flags` through
the trusted BTF pointer (`R1=trusted_ptr_scx_exit_info()`), no `bpf_probe_read_kernel`, no
tracefs. The control: `lockdown_probe.o`, one `exit` program that calls
`bpf_probe_read_kernel`, is refused on the same kernel:

```
4: (85) call bpf_probe_read_kernel#113
[    0.072479] Lockdown: vh-sched: use of bpf to read kernel RAM is restricted; see man kernel_lockdown.7
program of this type cannot use helper bpf_probe_read_kernel#113
```

**Is the link fd pollable** (the roadmap's [VERIFY])? Partly, and it matters for the
vh-init design. In 6.18 the struct_ops link has a `poll` operation
(`bpf_struct_ops_map_link_poll`, kernel/bpf/bpf_struct_ops.c): it reports `POLLHUP` once
the link has been detached. Measured: `BPF_LINK_DETACH` at 3029 ms, `poll` returns `0x10
HUP` at 3030 ms, the kernel says "disabled (unregistered from user space)", the exit record
(`SCX_EXIT_UNREG`) follows 1 ms later. But a kernel-side exit does not detach the link:
after `scx_bpf_error()` and after sysrq-S the fd reported nothing for the rest of the 6 s
hold (`revents 0x0`) while the scheduler was already disabled; `sched_ext` never calls
`bpf_link`'s detach. On colima's 6.8 the fd has no poll operation at all (poll returns the
default `POLLIN` at once) and `BPF_LINK_DETACH` is `EOPNOTSUPP`. Consequence: the manager
holds the link fd (closing it unregisters) and **wakes up on the ring buffer** that the
`exit` callback writes into: a ring buffer fd is pollable, and the exit record arrived 1-3
ms after the kernel's exit in every case (error, sysrq, detach). The roadmap's sentence
"held in epoll [VERIFY pollable]" becomes: epoll on the ring buffer, the link fd only for
the detach case.

**The sysrq reset bit** (the roadmap's [VERIFY the bit]). In kernel/sched/ext.c the `S`
key (`sysrq_handle_sched_ext_reset`, "reset-sched-ext(S)") and the `D` key (dump) are
registered with `enable_mask = SYSRQ_ENABLE_RTNICE`, which is `0x100` in
include/linux/sysrq.h. The bit is shared with `n` (nice all RT tasks); there is no bit
of its own, so the smallest `kernel.sysrq` that allows the reset from the keyboard is 256,
which also allows `n` and `D`. Test: `kernel.sysrq = 256`, `S` written to
`/proc/sysrq-trigger` after 2 s:

```
[   15.303253] sysrq: Disable sched_ext and revert all tasks to CFS
vh-sched: exit record from the ring buffer at 3025 ms: kind 67 (SCX_EXIT_SYSRQ), exit_code 0, flags 0x1
[   15.318556] sched_ext: BPF scheduler "vh_sched" disabled (disabled by sysrq-S)
vh-sched: sched_ext: state=disabled switch_all=0 enable_seq=3 nr_rejected=0 root/ops=(absent)
```

One caveat: `/proc/sysrq-trigger` does not consult the mask (`write_sysrq_trigger` calls
`__handle_sysrq(c, false)`); the mask governs the keyboard path. The keyboard path with
`kernel.sysrq = 256` is **[VERIFY on the GF63]**: Alt-SysRq-S must disable the scheduler
and Alt-SysRq-b must not reboot.

It rejects u128 and other compiler-rt calls, libc calls, signed division (v4), legacy
packet loads, bpf-to-bpf calls, a reachable `__bpf_trap`, a non-fetch atomic whose
operand register is read afterwards, a stack above 512 bytes, a missing `license`.

**The loader mechanics on a kernel without sched_ext** (colima, 6.8): the same loader
registers `tcp_ca_probe.o` as a `tcp_congestion_ops` struct_ops. While the link is held,
`/proc/sys/net/ipv4/tcp_available_congestion_control` reads `reno cubic vh_probe`; after
the close, `reno cubic`. This is the fast loop of the roadmap: ELF, BTF, maps, value and
link are exercised in a second on the Mac, and the 6.18 differences (poll, detach) are
the only ones found.

## What had to be learned

Every item was found by a verifier refusal or a wrong result and is now written down in
`sched/bpf/bpf.zig` and checked by the lint where a check is possible.

1. **A struct_ops callback receives its arguments as 8-byte slots**, not as the typed
   arguments: `R1=ctx()` points at `u64 args[]`, the verifier allows only 8-byte loads at
   slot offsets and types each slot from the member's prototype (`func 'exit' size 4 must
   be 8`, `invalid bpf_context access off=0 size=4`). C hides this in `BPF_PROG()`. In
   Zig: `export fn cb(ctx: *const bpf.Ctx)` and `ctx.ptr(0, *TaskStruct)`,
   `ctx.int(1, i32)`.
2. **Never `@panic` and never reach `unreachable`.** LLVM 22 lowers them to a call of the
   weak symbol `__bpf_trap`; the 6.18 verifier fails any program in which that call is
   reachable ("unexpected __bpf_trap() due to uninitialized variable?"), and 6.8 has no
   such kfunc at all. An error is `bpf.err("...")` (scx_bpf_error_bstr) and a normal
   return, exactly what `scx_bpf_error()` does in C. The lint flags `__bpf_trap`.
3. **Atomics.** `@atomicRmw(.Add, .monotonic)` is lowered to the non-fetch `lock *(u64
   *)(r +off) += r2`; when the result is used, the code goes on with the operand register
   as if it held the old value, so a counter test never fired. `.seq_cst` (or `.acq_rel`)
   gives `atomic64_fetch_add`. `@atomicLoad` does not exist on BPF ("Cannot select
   AtomicLoad"): read through `*volatile`. The lint flags a non-fetch atomic whose operand
   register is read next.
4. **A kfunc's non-const `char *` argument needs writable map memory**: a format string
   in the frozen `.rodata` is refused ("write into map forbidden, value_size=29"). The C
   macro uses `static char ___fmt[]`; `bpf.err` puts one buffer per message in `.data`.
5. **`const` globals are folded**, they never reach a map. The configuration is a `var`
   in `linksection(".rodata")`; the loader fills it (`--set`) and freezes the map, and the
   verifier then treats the values as constants (dead branches are not verified).
6. **A global may not carry its section's name**: `license` in the section `license`
   makes LLVM fail with "license changed binding to STB_GLOBAL"; it is `_license`.
7. **The verifier log at level 1 is rewound on success** (`do_check_common`, `pop_log`
   unless level 2): only the "processed N insns" line survives in the buffer and stale
   text follows its NUL. The loader cuts at the NUL and takes `insn_processed` from that
   line; the full trace needs level 2.
8. **BTF.** With ReleaseFast Zig/LLVM emits no BTF at all, which is fine: the kernel
   needs a BTF fd only for the struct_ops map (`btf_fd` must be a non-kernel BTF, syscall.c
   `map_create`) and optionally for the array maps. `btf.Builder` generates it at compile
   time from the Zig types with C names (`unsigned int`, `long long`, `vh_stats`), 659
   bytes, accepted by `BPF_BTF_LOAD` and by `map_check_btf`. The zbpf-style post-processor
   of LLVM's BTF, the fallback the roadmap planned, is not needed because nothing from
   LLVM's BTF is used; it stays an option for `func_info` if bpf-to-bpf calls are ever
   allowed.
9. **Sleepable members.** `scx_bpf_create_dsq` is `KF_SLEEPABLE` (6.18 ext.c:6102), so
   `init` is loaded with `BPF_F_SLEEPABLE`; `bpf_scx_check_member` allows sleepable
   programs only on `init`, `exit`, `init_task`, `cgroup_init`, `cgroup_exit`,
   `cgroup_prep_move`, `cpu_online`, `cpu_offline`.
10. **What the object looks like.** Zig emits REL relocations (not RELA): a kfunc call is
    `call -1` with `src_reg = 1` and `R_BPF_64_32` against the undefined symbol; a global
    is `ld_imm64` with `R_BPF_64_64` against the section symbol, the offset in the two
    `imm` fields; a `var` in `.rodata` gets its own section with the same name, so maps are
    keyed by section index; `.eh_frame` is emitted and ignored. The six kfuncs used resolve
    to FUNC ids in vmlinux BTF (6.18 arm64: `scx_bpf_dsq_insert` 22032,
    `scx_bpf_select_cpu_dfl` 22083).
11. **Zig 0.17 for this code**: `std.builtin.Optimize` is `.safe`/`.fast`; array
    repetition is `@splat`; `@typeInfo(T).@"struct".field_names/field_types`;
    `linux.errno(rc)`; `std.Target.bpf.cpu.v3` exists and enables alu32 and jmp32 (the
    `w` registers appear in the output); a comptime BTF build needs
    `@setEvalBranchQuota`.

## What is not shown

- Only QEMU: hvf on arm64, TCG on x86_64 (the Mac has no KVM for x86_64). Nothing ran on
  the GF63, as the rules require. The kernel-fat (Void configuration) run is open, see above.
- The scheduler is a FIFO with the default idle selection, not a policy: no weights, no
  cgroups, no vtime. The roadmap's v1 policy is the next step, not part of this spike.
- The `insn_processed` counts are for 105 instructions; the limit is 1,000,000. The v1
  policy will be a few thousand.
- bpf-to-bpf calls are refused by the loader and the lint on purpose (helpers are `inline
  fn`); if LLVM ever leaves a function out of line, the load fails with a clear message
  rather than silently supporting subprograms without `func_info`.
- The Zig 0.17.0 regressions listed in the roadmap did not touch this path.

## Recommendation

Go with the roadmap as written: the BPF part and the loader in Zig, no C anywhere.

- Fallback A (the policy in Zig user space, as scx_rustland) is not needed: a kfunc call
  from Zig costs nothing beyond a relocation, and the verifier accepts the trusted
  `task_struct` pointers.
- Fallback B (a bytecode emitter) is not needed: LLVM's BPF backend through Zig produces
  acceptable code; the three surprises (slots, `__bpf_trap`, atomics) are coding rules
  with a lint, not blockers.
- For vh-init: hold the link fd, epoll the exit ring buffer, treat `POLLHUP` on the link
  as the detach case; on an exit record, log the kind (names from the kernel's
  `scx_exit_kind` BTF enum) and restart with backoff.
- For CI: `vh-sched lint` after the x86_64 build; the KVM smoke test with the kernel-fat
  artifact once the user has dispatched that workflow.
- The emergency reset is `kernel.sysrq = 256` plus `vh-sched off` (closing the link);
  the keyboard path is to be checked on the laptop.
